手写一个只有 SKILL.md 的 Skill

认识最小 Skill 的文件结构，亲手写出一个用途明确的 error-explainer，再用它解释一条真实报错。

第 2 节 手写一个只有 SKILL.md 的 Skill

2.1 本节目标

认识最小 Skill 的文件结构，亲手写出一个用途明确的 error-explainer，再用它解释一条真实报错。

上一节解决了"为什么"，这一节解决"怎么写"。

2.2 先说清楚业务场景

先来看三个实际应用场景：

使用者用途价值
编程初学者看懂第一个关键错误，知道下一步该检查什么不用靠猜测反复改代码
老师或团队导师统一报错说明的格式减少重复的初步解释工作
项目新成员把本地运行失败整理成可转交的说明让后续求助带着证据，而不是只说"跑不起来"

新人在本地运行开发、构建和测试命令时，常常会把整段终端输出发给老师或团队成员，附一句"这是什么意思？"。回答者每次都要重新做同样几件事：

  1. 从大量输出中找到关键错误；
  2. 区分堆栈跟踪里哪些指向项目文件、哪些指向依赖库；
  3. 把英文报错换成新手能理解的说法；
  4. 告诉对方下一步先检查什么。

error-explainer 把这套重复流程固定下来。它的产出是一份可以继续排查或转交他人的报错说明：保留运行命令、退出码、错误原文、项目文件位置和未确认事项。

2.3 第一步：新建演示项目

打开终端，新建一个独立目录：

cd Documents
mkdir error-explainer-demo
cd error-explainer-demo
git init

git init 不是运行 JavaScript 的必需步骤。这里使用它，是为了把这个目录建成独立项目，后续创建的 Skill 和测试文件都能跟项目一起纳入版本管理。

在项目根目录新建 greeting.js，写入以下内容：

const user = { name: "Lin" };

console.log(`Hello, ${userName}!`);

此时项目结构如下：

error-explainer-demo/
└── greeting.js

用 Codex 打开 error-explainer-demo 目录。后续所有文件路径和命令均以该目录为起点。

保持终端位于 error-explainer-demo 目录，运行：

node greeting.js

你会看到类似下面的输出：

ReferenceError: userName is not defined
    at .../greeting.js:3:23

报错下面那一串以 at 开头的内容叫作堆栈跟踪。初学阶段不必全部看懂，先找第一条指向自己项目文件的记录即可——本例是 greeting.js:3:23，表示第 3 行、第 23 列。

程序还会返回退出码 1，表示未能正常执行完毕。终端通常不会主动显示退出码，可以在命令结束后立即查看：

# macOS 或 Linux
echo $?

# Windows PowerShell
$LASTEXITCODE

至此，我们已经拿到四项可以核对的事实：

  1. 错误类型是 ReferenceError；
  2. 错误原文是 userName is not defined；
  3. 出错位置是 greeting.js:3:23；
  4. 退出码是 1。

这些就是后面验证 Skill 的依据。

2.4 第二步：创建 Skill 目录

本节把 Skill 放在当前项目的 .agents/skills/ 目录下，方便跟仓库一起维护：

mkdir -p .agents/skills/error-explainer

个人跨项目使用的 Skill，通常放在 $CODEX_HOME/skills/；没有设置 CODEX_HOME 时，默认路径是 ~/.codex/skills/。本章先不展开，只使用项目目录。

2.5 第三步：写入 SKILL.md

一个 Skill 最少需要一个目录和一个 SKILL.md 文件：

error-explainer/
└── SKILL.md

将以下内容写入 .agents/skills/error-explainer/SKILL.md：

---
name: error-explainer
description: 用于开发入门、课程练习和团队新人培训，解释本地命令行报错和堆栈跟踪，把错误类型、出错位置、关键原文、通俗解释和下一步检查整理成可读、可转交的说明。用户表示看不懂终端报错，或要求解释某条本地命令为什么失败时使用；不要用于直接修改代码、安装依赖、访问生产环境或断言未经验证的根因。
---

# 新手报错说明

## 用途

用于开发入门、课程练习和团队新人培训。当用户在本地运行开发、构建或测试命令失败时，把终端输出整理成新手能看懂、也能转交给老师或团队成员的报错说明。

成功标准是：读者能知道哪条命令失败、最关键的错误是什么、应该先看哪个项目文件，以及下一步检查什么。

## 工作流程

1. 读取用户描述、错误原文、相关文件和项目说明，确认解释范围。
2. 如果用户提供了安全、明确的本地命令，运行一次并记录完整命令和退出码。
3. 保留错误类型和关键原文，不要先改写成自己的猜测。
4. 在堆栈跟踪中找到第一条指向当前项目文件的位置，记录文件和行号。
5. 用日常语言解释错误信息，再列出一到三个可以继续检查的方向。
6. 整理一句话说明、运行命令、退出码、错误原文、出错位置、通俗解释、下一步检查和未确认事项。

不要修改业务代码、测试、依赖、锁文件或配置。不要访问生产环境，也不要把"可能原因"写成已经确认的根因。

这就是一个可以使用的最小 Skill——它只有一个文件，没有脚本，也没有模板，但已经说清了服务谁、在什么场景使用、产出什么，以及怎样算成功。

2.6 第四步：看懂两个部分

SKILL.md 分成两个部分：

frontmatter 是文件开头两个 --- 之间的结构化配置，用来说明这是什么、什么时候使用。
Markdown 正文 说明被选中以后怎样工作。

frontmatter

文件开头两个 --- 之间的内容叫作 frontmatter。它是一段写在 Markdown 开头的结构化配置，不要求先学会 YAML。

最小版本只需要两个字段：

字段作用本例
nameSkill 的名称error-explainer
description做什么、什么时候用、什么时候不用解释本地报错，但不直接修改代码

description 不能太宽泛。下面这种写法没有区分度：

description: 帮助处理报错

Codex 无法判断"解释错误""直接修复代码"和"调查线上故障"是不是同一类任务。

description 要说明三个问题：

  1. 做什么：解释错误类型、位置和下一步检查。
  2. 什么时候用：用户看不懂本地命令行报错。
  3. 什么时候不用：直接改代码、访问生产环境或猜测根因。

Markdown 正文

frontmatter 解决"什么时候用"，正文解决"用了以后怎么做"。

正文应该直接写动作：

  1. 保留原文。
  2. 记录命令和退出码。
  3. 找到项目文件和行号。
  4. 解释错误类型。
  5. 给出下一步检查。

正文一定要写清动作边界。

2.7 第五步：显式调用 Skill

新建或安装 Skill 后，Codex 可能需要重新加载。最稳妥的做法是重启 Codex，再打开一个新会话。

$ 是调用 Skill 的符号。第一次测试时，直接用 $ + Skill 名称，这样可以显式调用 Skill，不受自动匹配影响：

$error-explainer 运行并解释 greeting.js 的报错。

这个提示词可以写得很简单，因为规则和流程在 $error-explainer 中已经约定好了。

查看返回结果，应该包含以下信息：

运行命令：node greeting.js
退出码：1
错误类型：ReferenceError
错误原文：userName is not defined
出错位置：greeting.js:3:23
通俗解释：程序在第 3 行使用了一个当前找不到定义的名称 userName。
下一步检查：比较第 3 行使用的名称和前面已经声明的名称是否一致。

注意最后一项是"检查"，不是"自动修复"。只有检查之后，才能确认具体原因。

如果 Codex 没有识别这个 Skill，依次检查：

  1. 文件路径是否为 .agents/skills/error-explainer/SKILL.md；
  2. 文件名是否严格写成 SKILL.md；
  3. frontmatter 是否包含 name 和 description；
  4. 是否已经重启 Codex 并打开新会话。

2.8 第六步：观察自动匹配

显式调用成功后，去掉 Skill 名称再试一次：

我看不懂 greeting.js 的终端报错。解释错误类型、文件位置和下一步检查，不要改代码。

如果 Codex 根据 description 自动选择了 error-explainer，说明触发描述基本有效。但自动匹配并非每次都能成功，Skill 较多时尤其需要注意。
