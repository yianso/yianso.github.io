cursor省tokens的一些方法

第一部分：立即见效的设置优化

1. 配置上下文窗口限制

预期节省：40-50% token

核心设置

打开 Cursor Settings (Cmd/Ctrl + ,)，调整以下参数：

{
  "cursor.contextLength": 4000,      // 从默认 8000 减半
  "cursor.maxTokens": 1000,          // 限制回复长度
  "cursor.longContextMode": false     // 非必要不开启长上下文
}

为什么有效

Cursor 会遵守这些限制来构建上下文。更小的窗口 = 更少的 token/请求，同时强迫 Cursor 只选择最相关的上下文。

什么时候需要恢复

  • 跨文件调试时
  • 大规模重构时
  • 学习不熟悉的代码库时

💡 技巧：可以根据任务类型动态调整，简单任务用 4000，复杂任务临时调到 8000。

3. 审计和优化 Cursor Rules

预期节省：每次请求减少 500-3,000 tokens

步骤 1：审计当前规则

在 Cursor 的 Ask Mode 中运行以下 prompt：

读取 @.cursor/rules/ 中的所有文件，估算每条规则的 token 数量。
按大小降序排列。找出哪些规则设置了 alwaysApply: true，
计算 always-apply 规则的总 token 成本。
建议哪些规则可以从 alwaysApply 改为 glob-scoped 或 agent-decided。

步骤 2：优化规则类型

规则内容推荐类型原因
项目总览（<50行）alwaysApply频繁需要，且体积小
代码风格规范glob-scoped (*.ts, *.tsx)只在编辑对应文件时需要
API 约定glob-scoped (src/api/**)只在 API 目录下需要
功能实现指南agent-decided让 Agent 判断是否相关
示例代码模板manual完全按需引用

步骤 3：引用而不是内联

# ❌ 差的做法：内联整个示例（浪费 token）
创建 API 路由时，遵循以下模式：
[200 行示例代码]

# ✅ 好的做法：引用文件（只在需要时加载）
创建 API 路由时，遵循 @src/routes/users.ts 中的模式。

💡 上下文指示器：Cursor 输入框有个上下文指示条，悬停可以看到当前激活的规则。

4. 关闭不必要的上下文源

关键设置

{
  "cursor.includeRecentEdits": false,    // 不发送编辑历史
  "cursor.includeOpenTabs": false,       // 只关注当前文件
  "cursor.codebaseIndexing": "selective" // 选择性索引
}

效果

  • 关闭 includeRecentEdits：避免发送你的编辑历史，减少每次请求约 500-2,000 tokens
  • 关闭 includeOpenTabs：避免发送所有打开标签页的内容，减少 3,000-5,000 tokens/标签页
  • 选择性索引：避免对整个代码库建立向量索引，RAG 检索更精准

什么时候需要重新开启

  • includeOpenTabs：多文件编辑时临时开启
  • includeRecentEdits：debug 需要上下文时临时开启

配合 .cursorrules 的选择性索引

# 只索引核心目录
@context include src/core
@context include src/utils

# 排除其他
@context exclude node_modules
@context exclude dist
@context exclude .next

第二部分：交互模式选择策略

5. 选择正确的交互模式

预期节省：50-75% tokens/session

各模式成本与适用场景

模式Token 消耗适用场景不适用场景
Tab (Autocomplete)500-2,000简单代码补全、变量名、函数签名复杂逻辑
Cmd+K (Inline Edit)1,000-3,000单函数编辑、添加 try-catch、类型标注多文件修改

决策流程图

你的任务是什么？
    |
    ├─ 补全一行代码 → Tab Autocomplete (最省)
    |
    ├─ 修改一个函数 → Cmd+K Inline Edit
    |
    ├─ 问一个问题/理解代码 → Ask Mode
    |
    ├─ 修改 1-3 个文件 → Agent Mode (谨慎提供上下文)
    |
    ├─ 大规模重构/新功能 → Agent Mode (先 Plan 再 Agent)
    |
    └─ 独立完整任务 → Background Agent (注意成本)

关键原则

  • 能用 Tab 解决的不用 Cmd+K
  • 能用 Cmd+K 解决的不用 Chat
  • 能用 Ask Mode 的不用 Agent Mode
  • Ask Mode 使用代码库索引检索，比 Agent Mode 逐文件读取高效得多

7. Max Mode 的精准使用

什么时候用 Max Mode

✅ 值得用的场景：

  • 需要理解大量代码上下文的复杂 debug
  • 使用 Gemini 时需要 >200k 上下文窗口
  • 需要一次性读取大文件（>250 行）避免多次工具调用

❌ 不值得用的场景：

  • 日常编码和小修改
  • 简单的代码问答
  • 不涉及大文件的任务

Max Mode 的隐藏收益

虽然 Max Mode 单次更贵（+20%），但在某些场景下反而更省钱：

普通模式读取大文件:  单文件上限 250 行 → 需要 3 次工具调用读取 750 行文件
                    3 次调用 × 重复上下文 = 大量冗余 token

Max Mode 读取大文件: 单文件上限 750 行 → 只需 1 次工具调用
                    1 次调用 × (1 + 20% 溢价) = 可能反而更省

💡 关键洞察：Max Mode 的 20% 溢价在减少工具调用次数时可能反而节省总成本。

第三部分：Prompt 工程与对话管理

8. 高效 Prompt 编写技巧

预期节省：2-5 倍 token 减少

黄金模板：[动作] + [目标] + [约束]

❌ 模糊的 prompt（Cursor 需要发送大量上下文来理解意图）:
"让这个更好"
"这里有问题，帮我看看"
"优化一下这个函数，它处理用户数据的时候很慢，因为它多次遍历数组..."

✅ 精确的 prompt（Cursor 知道确切范围，最小化上下文）:
"给 fetchUser 函数添加 TypeScript 类型"
"第 45 行的 user.email 添加 null 检查"
"将循环转换为 Map 实现 O(1) 查找"
"用 async/await 重构，保留错误处理"

指定文件和行号

❌ 让 Agent 自己搜索（触发多次文件读取）:
"修复认证模块的 bug"

✅ 直接指向位置（避免搜索开销）:
"修复 @src/middleware/auth.ts 第 87 行的 JWT 验证逻辑"

减少不必要的描述

❌ 过度解释（浪费 token 在你的描述上）:
"我正在尝试优化这个处理用户数据的函数，它运行很慢
 因为它多次遍历数组，我觉得我们应该用 map..."
(~50 tokens)

✅ 直接说需求（同样的结果，80% 更少的 token）:
"convert to Map for O(1) lookup"
(~8 tokens)

利用代码选择减少上下文

❌ 不选择代码直接在 chat 中问（Cursor 读取整个 500 行文件）:
→ 消耗 ~3,000 tokens 的文件上下文

✅ 先选中目标代码块，再 Cmd+K:
→ Cursor 只发送选中的代码 + ~50 行上下文
→ 消耗 ~500 tokens

9. 对话管理最佳实践

预期节省：减少 10 倍不必要的 token 消耗

核心规则：把对话当做临时的，而不是永久的

LLM 是无状态的，每条消息都会重新发送整个对话历史。

何时开启新对话

信号行动
完成了一个逻辑任务，要开始另一个新对话
Agent 在重复自己或引用过时信息新对话
切换到代码库的不同区域新对话
上下文指示器超过 60%新对话
对话超过 6-8 轮交互考虑新对话

前置上下文，而不是累积历史

❌ 渐进式构建上下文（浪费 3 倍 token）:
消息 1: "看看我们的 auth 模块"
消息 2: "现在也看看 user service"
消息 3: "好，给这两个添加限流功能"
→ 3 次往返，每次重发之前的全部内容

✅ 一次性提供所有上下文:
"给 API 添加限流功能，需要集成：
- @src/middleware/auth.ts（认证中间件）
- @src/services/user-service.ts（用户服务）
遵循 auth.ts 中的中间件模式。"
→ 1 次请求，包含所有必要信息

对话长度与成本关系

消息数  │ 累积 Token 消耗
────────┼──────────────────
  1     │ ██ (~5K)
  3     │ ██████ (~15K)
  5     │ ████████████ (~30K)
  10    │ ████████████████████████ (~60K)
  20    │ ████████████████████████████████████████████████ (~120K)

10. 先规划再实施的策略

Plan Mode 的价值

在请求代码之前，先让 AI 给出方案或计划。这可以：

  1. 减少不必要的迭代：避免「生成 → 不满意 → 重新生成」的循环
  2. 明确范围：让 AI 在规划阶段就确定需要修改哪些文件
  3. 节省 Agent 探索成本：Plan Mode 是只读的，不会触发文件修改

实践流程

步骤 1 (Plan Mode - 低成本):
"我需要给用户系统添加角色权限功能。
 请先给出实施方案：需要修改哪些文件，大致步骤是什么？"

步骤 2 (审查方案 - 0 token):
你阅读方案，确认方向正确。

步骤 3 (Agent Mode - 精准执行):
"按照以下方案实施：
 1. 在 @src/models/user.ts 添加 role 字段
 2. 创建 @src/middleware/rbac.ts 权限中间件
 3. 更新 @src/routes/admin.ts 添加权限检查"

特别适用于 Background Agent

先在本地用 Plan Mode 规划，然后把具体的计划交给 Background Agent：

  • 模糊指令 → Agent 大量探索 → 高成本
  • 具体计划 → Agent 精准执行 → 低成本

第四部分：文件与上下文管理

11. 最小可行上下文原则

核心思想

不要附加每一个「可能相关」的文件。只附加 Agent 确实需要的文件。

对比示例

❌ 过度上下文（浪费 token 在不相关文件上）:
"添加删除端点 @src/routes/users.ts @src/routes/posts.ts
 @src/routes/comments.ts @src/models/user.ts @src/models/post.ts
 @src/middleware/auth.ts @src/middleware/rate-limit.ts @src/lib/db.ts"
→ 8 个文件 × 3,000-5,000 tokens/文件 = 24,000-40,000 tokens 上下文

✅ 最小可行上下文:
"在 @src/routes/users.ts 中添加 DELETE /api/users/:id 端点。
 遵循该文件中已有的 PATCH 端点模式。"
→ 1 个文件 × 3,000-5,000 tokens = 3,000-5,000 tokens 上下文

使用 @folder 代替多个 @file

当需要概览目录结构时，使用 @folder 而不是逐个引用文件：

  • @src/routes/ 给出结构概览，比引用每个文件便宜得多
  • Agent 可以根据需要自行深入读取具体文件

信任 Agent 的探索能力

Agent 如果需要更多信息，它会自己去找。从最少上下文开始，让 Agent 按需补充。

⚠️ 注意：如果减少上下文后回答质量下降，说明你去掉了实际需要的上下文。逐步加回具体文件。

12. 大代码库的特殊策略

关闭自动代码库搜索

实测数据：关闭自动代码库搜索（RAG）可以将 token 消耗从 73,300 降到 31,800（减少 56% ）。

Dynamic Context Discovery

Cursor 引入了动态上下文发现（Dynamic Context Discovery）：

  • 不是预加载所有信息，而是让 AI 在需要时才获取
  • A/B 测试显示平均减少 46.9% 的 token 使用
  • 特别对 MCP 工具的效率提升明显

Monorepo 策略

  1. 创建强力 .cursorignore，排除非当前工作的包
  2. 使用 @folder 而不是 @codebase 来缩小范围
  3. 明确告诉 Agent 你在哪个包/模块中工作
  4. 考虑用 .cursorindexingignore 排除大型依赖包

15. Background Agent 成本管理

Background Agent 是最大的成本风险点，因为它：

  • 只使用 MAX mode（+20% 溢价）
  • 可以长时间自主运行
  • 消耗速率可达 Pro 计划的 5-10 倍

管理策略

  1. 拆分大任务
    ❌ 一个 $12 的复杂任务（效果可能不好） ✅ 三个 $4 的聚焦任务（效果更好，总成本相当）
  2. 提供具体的任务描述
    ❌ "优化项目性能"（Agent 会大量探索文件） ✅ "优化 src/utils/parser.ts 中 parseData 函数的性能， 将数组遍历改为 Map 查找，参考 src/utils/cache.ts 的模式"
  3. 先本地 Plan，再 Background Agent 执行
  • 在本地 Plan Mode 确定方案
  • 把具体步骤交给 Background Agent
  • 避免 Agent 在「理解需求」阶段浪费 token
  1. 设置消费限额
  • 在 Cursor Settings 中配置月度上限
  • 用第三方工具监控异常消费

16. 不同场景的最优策略组合

最优配置:
